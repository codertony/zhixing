## Context

知行平台 MVP 是一个全新建设项目，依托现有基础设施（GitLab、K8s 集群、MCP Server 工具链、大模型中转代理）进行上层能力建设。目标是在 10 人试点团队（4-5 个 Java/React 项目）上跑通端到端流程，为后续 100 个项目规模化推广奠定基础。

**现有可复用基础设施：**
- GitLab：代码仓库，支持 API 访问
- K8s 集群 + MCP Server 工具链：已就位，可直接部署新服务
- 大模型中转代理：已支持 OpenAI/Claude 等多模型路由
- 部分项目已有 `CLAUDE.md`/`AGENTS.md`，正在使用 Cursor/Claude Code

**核心约束：**
- 私有化部署，数据不出内网
- 知行平台是 Spec 规则的唯一事实来源（Source of Truth）
- 第一期 CI 只上报不拦截，避免影响现有研发流程
- 认知层 MCP 服务复用现有 K8s 集群部署

## Goals / Non-Goals

**Goals:**
- 建立三层 Spec 管理中心（公司/领域/项目），支持显式 override 与权限分层
- 实现 Spec 双轨分发（本地 CLAUDE.md 文件 + MCP 实时注入）
- 构建认知层 MCP 服务，索引 GitLab 代码 + 文档，支持代码语义问答
- 提供 CLI 智能体，预装公司 Spec 规范与认知层上下文
- 建立 Skill 仓库与分发机制
- CI 合规静态扫描数据上报（不拦截）
- 试点：10 人团队端到端跑通

**Non-Goals:**
- IM 沟通记录（Slack/飞书）接入（延后）
- CI 自动拦截违规提交（延后）
- 合规分析可视化仪表盘（延后）
- 跨公司/多租户场景
- 实时流式代码索引（第一期定期批量即可）

## Decisions

### D1：Spec 规则存储 — 数据库为主，Git 文件为产物

**选择**：知行平台关系数据库（PostgreSQL）为 Spec 规则唯一事实来源，`CLAUDE.md`/`AGENTS.md` 是分发产物。

**理由**：Spec 规则需要版本管理、权限分层、override 审计链路、合规率统计，这些用数据库比 Git 文件更易实现。Git 文件适合 IDE/CI 消费，由平台自动生成。

**备选方案**：GitOps（Git 为主，平台为 UI）→ 否决，原因：override 审计、权限分层、实时 MCP 注入在纯 Git 模型下实现复杂。

---

### D2：认知层索引策略 — 混合索引（向量 + 图谱）

**选择**：代码文件向量化（Embedding）存入向量数据库，代码依赖关系存入图数据库（或 PostgreSQL JSON），两者联合查询。

**理由**：语义问答（"这个模块是干什么的"）适合向量检索；依赖分析（"修改 A 影响哪些模块"）适合图结构。第一期可简化为纯向量方案，图谱后续迭代。

**第一期简化**：优先实现向量检索（Qdrant），图谱能力标记为 v2 迭代项。

---

### D3：Spec 分发触发机制 — 准实时 Webhook + 定期兜底

**选择**：Spec 规则变更时通过 Webhook 准实时推送 `CLAUDE.md`/`AGENTS.md` 到 GitLab；代码索引更新采用定期批量（如每日 2:00 AM）。

**理由**：Spec 规则变更频率低但时效性高（开发者立即需要感知）；代码变更频率高但对索引新鲜度要求不极致，定期批量降低系统压力。

---

### D4：CLI 智能体实现方式 — 基于 Claude Code 扩展，而非重新造轮子

**选择**：知行 CLI 作为 Claude Code 的上层封装/配置分发工具，通过自动注入 `CLAUDE.md`、挂载认知层 MCP Server 和 Skill MCP Server，实现差异化能力。

**理由**：Claude Code 已具备完整的工具调用、文件操作、Shell 执行能力。知行 CLI 的价值在于"预装上下文"，而非重复实现 Agent 底层能力。开发者运行 `zhixing init` 即可完成当前项目的上下文初始化。

**核心命令设计**：
- `zhixing init`：拉取当前项目 Spec，初始化 `CLAUDE.md`，挂载认知层 MCP
- `zhixing ask`：直接调用认知层问答
- `zhixing skill list/add`：查看/订阅 Skill

---

### D5：跨领域知识订阅 — MCP 服务端动态路由

**选择**：项目在 `CLAUDE.md` 中声明订阅的领域（如 `domains: [finance, procurement]`），认知层 MCP Server 根据订阅配置动态路由检索范围，而非在项目内预置所有领域知识。

**理由**：避免项目 context 窗口被无关知识污染；跨领域知识按需加载，降低索引维护成本。

---

### D6：技术栈选型

| 组件 | 选择 | 理由 |
|------|------|------|
| 后端服务 | Node.js 20 + Fastify | 与现有工具链一致，轻量，适合 MCP 服务 |
| Web 管理平台 | React 18 + TypeScript + Tailwind | 团队已熟悉，快速交付 |
| 向量数据库 | Qdrant | 轻量，支持私有化部署，K8s 可直接部署 |
| 关系数据库 | PostgreSQL | Spec 规则、Skill 元数据、合规记录存储 |
| 代码嵌入 | OpenAI Embeddings（通过中转代理） | 已有代理，直接复用 |
| MCP SDK | Anthropic MCP SDK | 标准协议，已有工具链支持 |

## Risks / Trade-offs

**[风险 1] 代码索引质量影响问答效果** → 缓解：第一期聚焦核心业务模块（而非全量仓库），建立评估基线，再逐步扩展范围。

**[风险 2] CLAUDE.md 被开发者手动修改后与平台状态不一致** → 缓解：`zhixing init` 加入检测逻辑，发现本地文件与平台版本不一致时提示重新同步；长期通过 CI 检查文件哈希。

**[风险 3] 三层规则 override 逻辑实现复杂** → 缓解：第一期只实现公司级 + 项目级（跳过领域级，试点团队小），领域级在第二期补全。

**[风险 4] 大模型 Embedding 调用成本** → 缓解：对代码文件按变更频率分级，高频变更文件增量更新，低频文件周期性全量刷新。

**[风险 5] 试点项目迁移已有 CLAUDE.md** → 缓解：提供迁移工具，将现有 `CLAUDE.md` 内容导入平台作为项目级 Spec，不强制一步到位。

## Migration Plan

1. **环境准备**：在 K8s 集群部署 PostgreSQL、Qdrant 实例，配置认知层 MCP 服务
2. **试点仓库接入**：选取 1 个 Java 后端 + 1 个 React 前端项目作为首批试点
3. **Spec 初始化**：在 Web UI 录入公司级基础规则，迁移试点项目的现有 `CLAUDE.md`
4. **认知层索引**：触发首次全量代码索引，验证问答质量
5. **CLI 分发**：试点开发者安装 `zhixing` CLI，执行 `zhixing init` 完成项目接入
6. **端到端验证**：以一个增量 feature 为基准，走完完整 AI 编程闭环
7. **CI 接入**：在试点项目 CI 中加入合规扫描步骤（只上报）

**回滚策略**：平台部署失败不影响现有研发流程（CI 合规扫描为可选步骤，`CLAUDE.md` 仍可手动维护）。
