# ZhiXing 常见反模式与纠正

## 概述

本文档列出知行平台开发过程中的常见反模式（Anti-Patterns）及其纠正方法，帮助开发者避免常见陷阱。

## 反模式 1: 跳过 Skill 直接编码

**错误**:
```
用户: "添加登录功能"
Claude: 直接开始写代码
```

**纠正**:
```
用户: "添加登录功能"
Claude: "这是一个新功能开发任务，我需要：
        1. 先调用 brainstorming Skill 探索需求
        2. 调用 security-review Skill 确保安全
        3. 然后使用 OpenSpec 流程创建规划"
```

## 反模式 2: 一次处理多个 Tasks

**错误**:
```
在一个 Session 中完成所有 tasks
```

**纠正**:
```
每次 Session 只处理一个 task
使用 Ralph Loop 或 /opsx:continue 跨会话推进
```

## 反模式 3: 未验证就标记 passes: true

**错误**:
```
实现后直接更新 tasks.json: passes: true
```

**纠正**:
```
实现 ──▶ 运行测试 ──▶ 检查覆盖率 >= 80% ──▶ 验证功能 ──▶ 更新 passes: true
```

## 反模式 4: 不使用 Ralph Loop 处理长任务

**错误**:
```
试图在一个 Session 完成大型重构
```

**纠正**:
```
大型任务:
1. /opsx:new 或 /opsx:ff 创建规划
2. /ralph-loop 启动持续迭代
3. 每个 task 完成后 commit
4. 通过 progress 文件保持状态
```

## 反模式 5: 跨层调用违规

**错误**:
```
L4 交互平面直接调用 L1 数据层
跳过控制平面和认知平面的约束
```

**纠正**:
```
L4 ──▶ L3 ──▶ L2 ──▶ L1
前端 ──▶ API ──▶ 业务逻辑 ──▶ 数据库
```

## 反模式 6: 忽略测试覆盖率

**错误**:
```
功能实现后没有添加测试
或者测试覆盖率 < 80% 就提交
```

**纠正**:
```
使用 TDD 流程：
1. 先写测试（红）
2. 实现功能（绿）
3. 重构优化
4. 确保覆盖率 >= 80%
5. 提交代码
```

## 反模式 7: 环境变量硬编码

**错误**:
```typescript
const API_URL = 'http://localhost:3000'
```

**纠正**:
```typescript
const API_URL = process.env.API_URL || 'http://localhost:3000'
```

## 反模式 8: 跳过 Git Commit

**错误**:
```
完成多个任务后才一次性 commit
或者任务完成后忘记 commit
```

**纠正**:
```
每完成一个任务，立即进行一次 git commit
提交信息格式：feat: 完成 [task-id] [task-description]
```

## 反模式 9: 不使用 Podman（本地开发）

**错误**:
```
本地开发使用 Docker Desktop
或者使用远程云 K8s 服务
```

**纠正**:
```
本地开发强制使用 Podman
rootless 模式更安全，与生产环境隔离
```

## 反模式 10: 任务失败后不重试直接放弃

**错误**:
```
任务执行出错后直接跳过或放弃
```

**纠正**:
```
任务出错后自动重试，最多 3 次
3 次失败后暂停并报告，等待人工介入
```

## 反模式 11: 不使用 JSON 格式存储任务清单

**错误**:
```
使用 Markdown 格式存储 tasks
模型容易误改，状态变更不清晰
```

**纠正**:
```
使用 JSON 格式存储功能清单（tasks.json）
结构化字段减少歧义，状态变更更清晰
```

## 反模式 12: 过早宣布完成

**错误**:
```
看到一些进度后就认为工作已完成
未验证所有验收标准
```

**纠正**:
```
完成所有 tasks 的验收标准验证
通过 /opsx:verify 检查
所有 passes: true 后才能归档
```

## 反模式 13: 忽略架构合规

**错误**:
```
代码引入循环依赖
跨层调用违规
```

**纠正**:
```
使用 madge 检查循环依赖
遵循四层架构约束
架构看护自动化检查
```

## 反模式 14: 长时间运行任务不使用检查点

**错误**:
```
大型重构或复杂功能开发没有进度记录
中断后无法恢复
```

**纠正**:
```
使用检查点执行模式
每个 artifact 和 task 完成后 git commit
维护 .progress.md 进度日志
```

## 反模式 15: 修复 Bug 不添加回归测试

**错误**:
```
直接修复 bug，不添加测试用例
相同 bug 可能再次出现
```

**纠正**:
```
修复前先添加失败的回归测试（红）
修复 bug 使测试通过（绿）
确保 bug 不会再次出现
```
